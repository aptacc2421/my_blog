## 1. The Agent Doesn't Generate Code

When we use agents like Codex or Claude Code, the thing actually "writing code" is the **remote large model**. The agent client (the program running on your machine) does not generate code itself—it doesn't generate, but it does do the "constructing the request text" work such as prompt assembly and tool-definition injection. Its core jobs are (all source references below are from the Codex repository `codex-rs/`, based on commit `57f42a8113`, 2026-08-06):

1. Send the conversation history + tool definitions to the remote model;
2. Receive the content returned by the model;
3. Execute commands and read/write files **locally**;
4. Send the execution results back to the model;
5. Loop until the task ends.

That raises the first question: the model returns a bunch of characters—how does the Agent know which part is "what I want to say" versus "I want to run `git status`"? It can't rely on scanning for special strings, can it?

<a id="structured-events"></a>

## 2. How the Agent "Reads" Model Output: A Structured Event Stream

The answer: **the model doesn't output a blob of raw characters at all—it outputs a stream of typed, structured JSON events**, continuously pushed by the server and parsed one by one by the client, with no need for repeated polling.

In Codex these events are modeled as a Rust enum called `ResponseItem` ([`codex-rs/protocol/src/models.rs:816`](https://github.com/openai/codex/blob/57f42a8113/codex-rs/protocol/src/models.rs#L816)); each variant is a kind of "identity tag":

```rust
// codex-rs/protocol/src/models.rs:816 (excerpt; omitted fields marked with comments, not the full source)
pub enum ResponseItem {
    Message { role: String, content: Vec<ContentItem>, /* ... other fields */ },
    FunctionCall { arguments: String, call_id: String, /* ... other fields */ },
    FunctionCallOutput { call_id: String, output: FunctionCallOutputPayload, /* ... other fields */ },
    // ... other variants
}
```

| Variant | Meaning |
|------|------|
| `Message` ([`models.rs:825`](https://github.com/openai/codex/blob/57f42a8113/codex-rs/protocol/src/models.rs#L825)) | Plain-text reply |
| `FunctionCall` ([`models.rs:878`](https://github.com/openai/codex/blob/57f42a8113/codex-rs/protocol/src/models.rs#L878)) | Tool-call request (includes `name`, `call_id`, `arguments`) |
| `FunctionCallOutput` ([`models.rs:918`](https://github.com/openai/codex/blob/57f42a8113/codex-rs/protocol/src/models.rs#L918)) | Tool execution result (sent back to the model) |
| `WebSearchCall` etc. | Other capabilities |

Once the Agent receives an event, it only needs to `match` on this enum—seeing `FunctionCall` it parses the arguments and executes locally; seeing `Message` it displays to the user. It **does not need to guess from string content at all**; the identity comes with the type.

<a id="memory-from-history"></a>

## 3. Where the Model's "Memory" Comes From: Resending the Full History

Agent conversations have an obvious "context" notion—you mention changing some function in one message, and it still remembers in the next. Where does that memory come from?

A common but wrong answer is "the KV cache." But that's not it:

- **The KV cache** classically accelerates a single inference run (the sequential decoding within one request). Analogy: the model emits text one token at a time, and each new token must "look back" at all preceding tokens; the KV cache stores the computed key/value state of that "look back" to avoid recomputation. It is essentially a **cache of computational state**, and it does not mean the model remembers a conversation across requests—modern inference systems have extended it to cross-request prefix reuse (Prefix Caching, see below), but what gets cached is computational state, not the user's semantic "memory."
- For a stateless inference API, the model server **does not automatically save your session history**; if a provider offers conversation-management features like conversation ids or assistants, those are a separate mechanism that must be explicitly enabled. What it "remembers" depends entirely on **which context you put into this particular request**.

One point worth clarifying to avoid confusion: modern servers do perform **cross-request KV reuse** (Prefix Caching, detailed in the next section), but that is a server-side caching optimization for "repeated prefixes," which is a different thing from "the model remembers the conversation"—even if caching saves the compute for the prefix, the input the model sees is still the context you fully supplied this time.

Before every request to the model, Codex clones the **entire conversation history** as input ([`codex-rs/core/src/session/turn.rs:335`](https://github.com/openai/codex/blob/57f42a8113/codex-rs/core/src/session/turn.rs#L335)):

```rust
// Construct the input that we will send to the model.
let sampling_request_input: Vec<ResponseItem> = async {
    sess.clone_history().await.for_prompt(...)  // clone the full history
}
```

What is in this "full history"? **In Codex, every one of your messages, every model output, every tool call in between, and every tool execution result—all of it is resent verbatim.** In other words, the model "remembers" earlier events not because it kept a ledger on the server, but because you read the entire chat transcript back to it every time. (Different agents use different strategies: some trim, some retrieve, some resend only the most recent turns—see Section 5.)

This is a deeply counterintuitive, almost "frightening" conclusion: when we ask an agent to carry out a large coding task, **our conversation may be only a few hundred characters, but every request resends a huge amount of code and tool outputs**—all so the model can "remember" where things stand now.

<a id="prefix-caching"></a>

## 4. If It Resends Everything Every Time, Isn't That Expensive? — The Mitigation and Limits of Prefix Caching

The server obviously knows this is expensive, so it provides **Prefix Caching**: if the beginning of a new request matches the previous one, the server reuses the KV state already computed for that segment, at a much lower price. Discounts vary by provider and are often dramatic—here is a price comparison of two mainstream 2026 models (the two are in different currencies, so absolute values can't be compared directly; the comparable metric—and the focus of this article—is the discount multiple):

| Model | Input (cache miss) | Input (cache hit) | Discount | Context window |
|------|------|------|------|------|
| **DeepSeek V4 Flash** (2026-08-07 example price) | CN¥1 / 1M tokens | CN¥0.02 / 1M tokens | **50×** | ~1M |
| **OpenAI GPT-5.6 Sol** (2026-08 official pricing) | $5.00 / 1M tokens | $0.50 / 1M tokens | **10×** | 1.05M |

> A detail from the GPT-5.6 Sol pricing page that happens to support "longer conversations cost more": **when prompt input exceeds 272K tokens, the entire request is billed at 2× input and 1.5× output**—once history crosses the threshold, the per-token price jumps as a whole, which has a more direct effect than the cache discount.
>
> Note: this 272K is OpenAI's **billing tier threshold**, which numerically equals some models' context window but means something entirely different (one is a billing rule, the other a model configuration)—see Section 5.

One clarification: Codex sends a cache key in the request (defaulting to `session_id`, [`codex-rs/core/src/client.rs:483`](https://github.com/openai/codex/blob/57f42a8113/codex-rs/core/src/client.rs#L483)) to mark "still the same session," but **whether and how the server uses it to implement prefix caching is decided by the model serving implementation**—we cannot derive the server's actual caching implementation from the Codex source.

But caching **only saves the cost of "recomputing the prefix"**—it can't save you from something else: **the growth in attention computation**.

If you think of the model processing its input as a matrix in which "every token is scored against every other token": with n tokens of history, the attention matrix is n×n. For simplicity we ignore multi-head attention (in reality it is h such n×n matrices, h being the number of heads) and block-based optimizations like FlashAttention, and look only at the order of magnitude of the compute. Each new token grows the matrix from n×n to (n+1)×(n+1), **adding (n+1)² − n² = 2n+1 cells**:

```
100  token → 101  token: adds 2×100+1  = 201   cells
10000 token → 10001 token: adds 2×10000+1 = 20001 cells
```

Strictly speaking, this is about the scale of the **self-attention** part: it grows quadratically with sequence length. But total inference compute isn't just attention—each layer also has a huge feed-forward network, the MLP (complexity O(n·d²), d being the hidden dimension), which in many models with large d actually dominates. So the precise statement is: **self-attention has O(n²) growth, and overall inference cost also depends on the model architecture.** Looking only at the attention-matrix scale, as the conversation advances and history lengthens:

- From 100 tokens to 10000 tokens, the attention matrix grows from 100² = 10⁴ to 10000² = 10⁸—**a factor of 10000**;
- Even with a full prefix-cache hit, the incremental compute of the last step grows linearly with history length—from 201 cells to 20001 cells, **roughly 100×**.

We should also clarify the prefill/decode distinction: the n×n above is the scale of **prefill** (processing the entire history at once). With the KV cache enabled, each newly generated token only matches its query against the cached keys/values, which is **O(n) incremental compute**—"the last step grows linearly" refers exactly to this.

The worst case: **you reopen this conversation after a long time.** The server's prefix cache has most likely been evicted, and the hit is gone. This isn't "just compute the new increment"—the entire history must be re-prefilled from scratch. In terms of theoretical scale, re-running a long prompt's prefill differs by an order of magnitude from the decode of a few appended tokens (O(n²) vs O(n)); the actual gap depends on the inference framework, batch state, and caching implementation. And on the billing side, history returns from the discounted prefix price to the full price (for DeepSeek V4 Flash, from CN¥0.02 to CN¥1 per million tokens—**a 50× jump on the bill**). **And this is just a single interaction of "continuing a long conversation."**

Putting Section 4 together, you'll find there are actually **three distinct ledgers** here, often conflated:

| Layer | What it is | How it grows as history lengthens |
|------|--------|----------------|
| **Input token count** | The "volume" you resend every request | Linear O(n): the longer the history, the more you resend each time |
| **What you pay** | Billed per token, but the **unit price isn't constant** | "Volume" linear × "unit price" fluctuating: cache hit/miss, peak/off-peak, and tier jumps all change the unit price |
| **Vendor compute** | The real computation to process this request | self-attention part O(n²), MLP O(n·d²); with a prefix-cache hit the old prefix is reusable, while the added portion grows linearly with history length |

Two key distinctions: **these three costs are independent of one another**—a cache discount lowers the price but doesn't change the physical compute of attention (the specific discount ratio is a pricing policy, not "derived" from hardware cost); tiered billing can make the bill jump without any jump in compute.

<a id="compression"></a>

## 5. Compaction: Another High-Cost Remedy

History doesn't grow without bound—when token usage hits an upper limit, Codex triggers **compaction**, replacing the old history with a summary. What is the limit? It depends on the model's **context window** (the maximum number of tokens the model can handle in a single call):

```rust
// codex-rs/model-provider/src/provider.rs:552 —— one model example
"context_window": 272_000,
"max_context_window": 272_000,
```

> Context windows vary greatly between models: this is one example from Codex's official models (272K), while DeepSeek V4 Flash has a context of **about 1M tokens**, with the 95% headroom hard cap around 950K (note: this is only a backstop limit to prevent overruns; the daily compaction trigger is the independent `auto_compact_token_limit` budget, usually smaller). Incidentally, this 272K and the 272K billing threshold from Section 4 are merely a numerical coincidence—the former is a context-window configuration, the latter a billing-tier rule; the two are unrelated.

But first, a distinction: **the routine compaction trigger is not "95% of the context window" but an independent token budget, `auto_compact_token_limit`**—which can come from the config `model_auto_compact_token_limit` or from model metadata ([`codex-rs/models-manager/src/model_info.rs:35`](https://github.com/openai/codex/blob/57f42a8113/codex-rs/models-manager/src/model_info.rs#L35)); it is usually much smaller than the context window (if no such budget is configured, it falls back to the hard window limit as the sole trigger), and a fallback buffer is added on top. Also, Codex doesn't use 100% of the window; it keeps headroom (default `effective_context_window_percent = 95`, see [`codex-rs/models-manager/src/model_info.rs:172`](https://github.com/openai/codex/blob/57f42a8113/codex-rs/models-manager/src/model_info.rs#L172); overridable via config)—**95% of the window is only a hard backstop to prevent request overruns, not the routine compaction trigger**. The actual effective cap is computed by `model_context_window()` ([`codex-rs/core/src/session/turn_context.rs:238`](https://github.com/openai/codex/blob/57f42a8113/codex-rs/core/src/session/turn_context.rs#L238)): for a 272K window at the default 95%, that's 272_000 × 95 / 100 ≈ **258K tokens**.

The compaction decision is "auto-compact budget exceeded **or** hard window limit reached," whichever comes first ([`codex-rs/core/src/session/context_window.rs:76`](https://github.com/openai/codex/blob/57f42a8113/codex-rs/core/src/session/context_window.rs#L76)):

```rust
let full_context_window_limit_reached =
    full_context_window_limit.is_some_and(|limit| active_context_tokens >= limit);
let token_limit_reached = buffered_auto_compact_limit
    .is_some_and(|limit| auto_compact_scope_tokens >= limit)
    || full_context_window_limit_reached;
```

**Compaction isn't triggered only by "tokens used up."** Pre-sampling before a request is sent, exceeding the token budget mid-turn, and model switches (e.g., to a model with a smaller context window) all cause Codex to compact the old history before continuing.

**But compaction itself is a full model request, and not a cheap one**: the client must send the **full history** (along with the summarization instruction) to the model once more, have it condense the old history into a handoff summary, then rebuild a shorter history of "retained old history + summary" to replace the original. Compaction can be executed by the server or the client, but **either way, the full history has to be sent to the model for processing once**. Other agents may use different strategies such as trimming, retrieval, or incremental summarization.

In the extreme case triggered by the hard window limit, this request's input can reach **about 258K tokens** (if triggered by `auto_compact_token_limit`, the input size depends on that budget's configured value, usually smaller). If the original conversation was only 1000 tokens, the cost of this single compaction can be **hundreds of times** the original conversation—and that's just the "one-time housekeeping fee" paid to preserve context.

Another detail corroborating that compaction really does "send everything": on the local-compaction path, if the history is so long that even the compaction request itself overruns the limit, Codex **deletes one item from the very front of the history and retries** ([`codex-rs/core/src/compact.rs:304`](https://github.com/openai/codex/blob/57f42a8113/codex-rs/core/src/compact.rs#L304)); the source comment explicitly says trimming from the front is to preserve the prefix cache—proving it really is sending the whole thing, until it can't fit anymore.

Finally, combining the billing and compaction mechanisms yields a counterintuitive conclusion. Take GPT-5.6 Sol: its context window is a huge **1.05M**, so even at the default 95% hard cap, compaction wouldn't happen until about **997K**; yet billing already doubles the entire request at **272K**. In other words, **for models with tiered billing like GPT-5.6 Sol, the price cliff comes far earlier than the compaction trigger**—whether to compact early or start a new conversation is driven mainly by the billing threshold, not by context capacity (purely linear-billed models like DeepSeek have no "cliff," so this conclusion doesn't apply). The context isn't full yet—the wallet is.

## 6. Clarifying an Intuitive Assumption: Is Continuing an Old Conversation Really Cheaper Than a New One?

Some people assume "continuing an old conversation gets a prefix-cache hit, so it must be cheaper than starting a new one." Let's run the numbers.

Suppose the old conversation has 10000 tokens and this turn adds 100 tokens of new instructions. You choose to summarize the old history into a 200-token summary and start a new conversation (but the 100 tokens of new instructions this turn must be sent whether you continue or start fresh). All priced at DeepSeek V4 Flash rates (2026-08-07, off-peak example price):

- **Continue the old conversation**: assume the old-history prefix fully hits cache—old history 10000 × CN¥0.02 / million = **CN¥0.0002**, new 100 × CN¥1 / million = **CN¥0.0001**, total **CN¥0.0003**;
- **If the cache misses**: old history at the miss price 10000 × CN¥1 / million = **CN¥0.01**, total **CN¥0.0101**;
- **Start a new conversation**: summary 200 + new instructions 100 = **300 tokens**, at the miss price 300 × CN¥1 / million = **CN¥0.0003**.

The comparison is interesting:

- **Cache hit**: continuing costs CN¥0.0003 = new conversation CN¥0.0003, **nearly a wash**—the 50× discount cancels out the cost of resending history entirely;
- **Cache miss**: continuing at CN¥0.0101 is **about 34×** the CN¥0.0003 of a new conversation;
- Look at the bill structure—even with the cache hit's 50× discount, **the earlier history (CN¥0.0002) is still 2× the new content (CN¥0.0001), i.e., 67% of the bill**. The discount only makes "old history" cheaper; but when history is large enough, it remains the bulk of the bill.

Switch to **GPT-5.6 Sol** (only a 10× cache discount, billed in USD), and the same math is starker:
- **Continue (cache hit)**: 10000 × $0.50 / million + 100 × $5.00 / million = **$0.0055**;
- **Continue (cache miss)**: 10000 × $5.00 / million + 100 × $5.00 / million = **$0.0505**;
- **New conversation**: (200 + 100) × $5.00 / million = **$0.0015**.

On a cache hit, continuing ($0.0055) is still **3.7×** a new conversation ($0.0015)—a 10× discount can't make up for the cost of resending history; on a miss, again about **34×**. Compare: **with a cache hit, DeepSeek's 50× discount makes continuing ≈ new, while GPT-5.6 Sol's 10× discount makes continuing 3.7× more expensive—the smaller the discount, the pricier continuing becomes.**

> Worth noting: this only considers the **token cost of a single request**. Starting a new conversation saves the "resend history" money, but your own effort in condensing it into a 200-token summary has a cost (time, or the fee of having the model summarize), and degraded summary quality can make the model err in later turns, burning more tokens across rounds—the true cost may not be lower. Also, the above uses **off-peak** prices; if the prevailing tier is higher (e.g., DeepSeek doubling during peak), absolute costs rise overall, but the **ratio** between continuing and new stays the same, so this section's conclusion doesn't depend on peak vs. off-peak.

The key variables are **whether the cache hits and how large the discount is**: the larger the discount (like DeepSeek's 50×), the closer continuing an old conversation gets to "nearly free," and a new conversation's cost advantage is canceled out—at the price of losing context. Conversely, if the provider **doesn't implement prefix caching** (e.g., some relay/proxy services), old history is billed at the full miss price—the longer the history, the bigger the loss, and then "summarize it yourself and start a new conversation" is a very sensible choice. Going further, for models like GPT-5.6 Sol where input over 272K doubles the entire request, once history crosses the threshold, the unit price of continuing jumps as a whole. The attention compute is the same story: continuing's incremental compute (≈2×10000 = 20000 cells) is already about twice a new conversation's full compute (100×100 = 10000 cells).

So why do we still continue old conversations? Because **a new conversation has no context**—the model doesn't remember previous decisions, constraints, or progress. So this is a pricing dilemma:

> **If you want context, you keep paying for ever-lengthening history; if you want cheap, you drop the context and start from zero.**

<a id="conclusion"></a>

## 7. Conclusion

Pulling the whole article together, the core fact is just one: **from the API consumer's perspective, large models are usually stateless—every new inference request requires the client to re-supply the current context.**

- How does the Agent understand model output?—Via a **typed, structured event stream**, not by scanning strings.
- Where does the model's "memory" come from?—From **resending the full history every time**, not from the KV cache.
- How do the costs grow?—See the three ledgers in Section 4: token count grows **linearly**, unit price **fluctuates**, self-attention grows **quadratically**; prefix caching mitigates but doesn't eliminate it.
- What happens when you overrun the limit?—**Compaction**, but compaction itself is a full-resend request and is expensive.
- New conversation vs. continuing?—A new conversation is cheap but has no context; continuing is expensive but remembers.

Understand this, and you understand why long sessions burn so much money, why agents need compaction, and why "cache" and "memory" are two completely different concepts. **Context is not a property of the model—it's something you buy with tokens.**
