## 1. Agent 不生成代码

当我们使用 Codex、Claude Code 这类 Agent 时，真正"写代码"的是**远程的大模型**。Agent 客户端（跑在你本地的那套程序）本身不负责生成代码——它不生成，但会做 prompt 拼接、工具定义注入这类"构造请求文本"的工作。它的核心任务是（下文所有源码引用均来自 Codex 仓库 `codex-rs/`，基于 commit `57f42a8113`，2026-08-06）：

1. 把对话历史 + 工具定义发给远程模型；
2. 接收模型返回的内容；
3. 在**本地**执行命令、读写文件；
4. 把执行结果回传给模型；
5. 循环，直到任务结束。

那么第一个问题就来了：模型返回的是一堆字符，Agent 怎么知道哪部分是"我要说的话"、哪部分是"我要执行 git status"？总不能靠扫描特殊字符串吧？

<a id="structured-events"></a>

## 2. Agent 如何"看懂"模型的输出：结构化事件流

答案是：**模型输出的根本不是一坨裸字符，而是一条条带类型的结构化 JSON 事件流**——由服务端持续推送、客户端逐条解析，无需反复轮询。

这些事件在 Codex 里被建模成一个 Rust 枚举 `ResponseItem`（[`codex-rs/protocol/src/models.rs:816`](https://github.com/openai/codex/blob/57f42a8113/codex-rs/protocol/src/models.rs#L816)），每个变体就是一种"身份标签"：

```rust
// codex-rs/protocol/src/models.rs:816（节选；省略的字段以注释标注，非完整源码）
pub enum ResponseItem {
    Message { role: String, content: Vec<ContentItem>, /* ... 其余字段 */ },
    FunctionCall { arguments: String, call_id: String, /* ... 其余字段 */ },
    FunctionCallOutput { call_id: String, output: FunctionCallOutputPayload, /* ... 其余字段 */ },
    // ... 其他变体
}
```

| 变体 | 含义 |
|------|------|
| `Message`（[`models.rs:825`](https://github.com/openai/codex/blob/57f42a8113/codex-rs/protocol/src/models.rs#L825)） | 纯文本回复 |
| `FunctionCall`（[`models.rs:878`](https://github.com/openai/codex/blob/57f42a8113/codex-rs/protocol/src/models.rs#L878)） | 工具调用请求（含 `name`、`call_id`、`arguments`） |
| `FunctionCallOutput`（[`models.rs:918`](https://github.com/openai/codex/blob/57f42a8113/codex-rs/protocol/src/models.rs#L918)） | 工具执行结果（回传给模型） |
| `WebSearchCall` 等 | 其他能力 |

Agent 收到事件后，只需要 `match` 这个枚举——看到 `FunctionCall` 就解析参数并本地执行，看到 `Message` 就显示给用户。它**完全不需要靠猜测字符串内容**来区分，身份是类型带过来的。

<a id="memory-from-history"></a>

## 3. 模型的"记忆"从哪来：全量重发历史

Agent 的对话有明显的"上下文"概念——你上一句说改某个函数，它下一句还记得。那这个记忆是从哪来的？

一个常见的错误答案是"KV cache"。但它并不是答案：

- **KV cache** 经典上是单次推理过程（一次请求内的连续解码）的加速缓存。打个比方：模型生成文字是一个字一个字往外蹦的，每蹦一个新字都要"回头看"前面所有字；KV cache 就是把"回头看"算好的 key/value 状态存下来，避免重复计算。它本质上是**计算状态的缓存**，并不代表模型记住了跨请求的对话——现代推理系统虽把它扩展到了跨请求的前缀复用（Prefix Caching，见下），但缓存的是计算状态，不是用户语义上的"记忆"。
- 对无状态的推理 API，模型服务端**不会自动保存你的会话历史**；若服务商提供 conversation id、assistants 这类会话管理能力，那也是需要显式启用的另一套机制。它"记得"什么，完全取决于你这次请求里**塞了哪些上下文**。

需要先澄清一个容易混淆的点：现代服务端确实会做**跨请求的 KV 复用**（Prefix Caching，下一节详述），但那属于服务端对"重复前缀"的缓存优化，与"模型记得对话"是两回事——就算缓存把前缀的算力省了，模型看到的输入仍然是你这次完整提供的上下文。

Codex 每次向模型发请求前，都是把**整个对话历史**克隆出来作为输入（[`codex-rs/core/src/session/turn.rs:335`](https://github.com/openai/codex/blob/57f42a8113/codex-rs/core/src/session/turn.rs#L335)）：

```rust
// Construct the input that we will send to the model.
let sampling_request_input: Vec<ResponseItem> = async {
    sess.clone_history().await.for_prompt(...)  // 克隆全部历史
}
```

这"全部历史"里有什么？**在 Codex 中，你的每条消息、模型每次的输出、期间每一次工具调用、每一次工具执行的结果——全部原样重发。** 换句话说，模型"记得"之前的事，不是因为它在服务器上记了账，而是因为你每次都把整本聊天记录重新念给它听。（不同 Agent 策略各异：有的裁剪、有的检索、有的只重发最近几条，见第 5 节。）

这是一个非常反直觉、甚至有点"恐怖"的结论：当我们让 Agent 执行大型代码任务时，**我们的对话可能只有几百个字，但它每次请求都要把海量的代码、海量的工具调用结果全部重发回去**，只为让模型"记得"现在做到哪一步了。

<a id="prefix-caching"></a>

## 4. 既然每次都重发，那不是巨贵吗？—— Prefix Caching 的缓解与极限

服务端当然也知道这样很贵，于是提供了 **Prefix Caching（前缀缓存）**：如果新请求的开头跟上一个请求一样，服务端就复用那段已算好的 KV 状态，大幅降价。折扣因服务商而异，而且常常非常夸张——下面两家 2026 年主流模型的价格对比（两家货币不同、绝对值不可直接比，可比的、也是本文关注的是**折扣倍数**）：

| 模型 | 输入（缓存未命中） | 输入（缓存命中） | 折扣 | 上下文窗口 |
|------|------|------|------|------|
| **DeepSeek V4 Flash**（2026-08-07 示例价） | 1 元 / 1M token | 0.02 元 / 1M token | **50 倍** | ~1M |
| **OpenAI GPT-5.6 Sol**（2026-08 官网定价） | $5.00 / 1M token | $0.50 / 1M token | **10 倍** | 1.05M |

> 顺带一个来自 GPT-5.6 Sol 定价页的细节，正好佐证"长对话更烧钱"：**提示词输入超过 272K token 时，整段请求按输入 2×、输出 1.5× 计费**——历史一旦跨过阈值，单价整体跳档，比缓存折扣的影响更直接。
>
> 注意：这个 272K 是 OpenAI 的**计费跳档阈值**，与某些模型的 context window 数值相同但含义完全不同（一个是计费规则、一个是模型配置），详见第 5 节。

需要说明：Codex 会在请求里带一个缓存 key（默认取 `session_id`，[`codex-rs/core/src/client.rs:483`](https://github.com/openai/codex/blob/57f42a8113/codex-rs/core/src/client.rs#L483)）来标识"还是同一个会话"，但**服务端是否以及如何利用它实现 prefix caching，由模型服务实现决定**——我们无法从 Codex 源码推出服务端的具体缓存实现。

但缓存**只是省"重算前缀"的钱**，它救不了另一件事——**attention 计算量的膨胀**。

如果把模型处理输入的过程看成一个"所有 token 两两打分"的矩阵：历史有 n 个 token，注意力矩阵就是 n×n。简化起见，我们忽略多头注意力（实际是 h 个 n×n 矩阵，h 为头数）和 FlashAttention 等分块优化，只看计算量的量级。每新增一个 token，矩阵从 n×n 变成 (n+1)×(n+1)，**新增 (n+1)² − n² = 2n+1 个格子**：

```
100  token → 101  token：新增 2×100+1  = 201  格
10000 token → 10001 token：新增 2×10000+1 = 20001 格
```

严格说，这里说的是 **self-attention 部分**的规模：它随序列长度二次方累积。但推理的总计算量不只有 attention——每层还有一个巨大的前馈网络 MLP（复杂度 O(n·d²)，d 为隐藏维度），在很多 d 很大的模型里它甚至占大头。所以准确表述是：**self-attention 存在 O(n²) 的增长，整体推理成本还取决于模型结构**。只看 attention 矩阵规模，随着对话推进、历史越来越长：

- 从 100 token 涨到 10000 token，attention 矩阵从 100² = 10⁴ 涨到 10000² = 10⁸，**差了 10000 倍**；
- 即便前缀缓存全命中，最后一步的增量计算量也随历史长度线性放大——从 201 格涨到 20001 格，**增幅约 100 倍**。

需要澄清 prefill 与 decode 的区别：上面的 n×n 是 **prefill**（一次性处理整段历史）的量级；启用 KV cache 后，每生成一个新 token 只把它的 query 与已缓存的 key/value 做一次匹配，是 **O(n) 的增量计算**——"最后一步增量线性放大"说的正是这个。

最坏的情况是：**隔了很久才重新打开这个对话**。服务端的前缀缓存大概率已被清理，命中失效。此时不是"只算新增的增量"，而是要把整段历史从头重新 prefill 一遍——从理论量级看，重跑长 prompt 的 prefill 与仅追加少量 token 的 decode 存在数量级差异（O(n²) vs O(n)）；实际差距取决于推理框架、batch 状态与缓存实现。而计费上，历史也从前缀折扣价回到全价（对 DeepSeek V4 Flash 就是从 0.02 元 / 百万涨到 1 元 / 百万，**账单直接差 50 倍**）。**这只是"续一个长对话"本身的一次交互。**

把第 4 节串起来，你会发现这里其实涉及**三层账本**，经常被混为一谈：

| 层面 | 是什么 | 随历史变长怎么涨 |
|------|--------|----------------|
| **输入 token 数** | 你每次请求重发的"量" | 线性 O(n)：历史越长，每次重发越多 |
| **你付的钱** | 按 token 计费，但**单价不恒定** | "量"线性 × "单价"波动：缓存命中/未命中、峰谷、跳档都会改变单价 |
| **厂商算力** | 处理这次请求的真实计算 | self-attention 部分 O(n²)、MLP O(n·d²)；前缀缓存命中时旧前缀可复用，新增部分随历史长度线性放大 |

两个关键区别：**这三层代价互相独立**——缓存折扣能降价，但不改变 attention 的物理计算量（具体折扣比例是定价策略，不是从硬件成本"算"出来的）；阶梯计费能让账单跳变，但不代表算力突变。

## 5. 压缩：另一种高代价的补救

历史不会无限膨胀——当 token 用量到达某个上限，Codex 就会触发**压缩**，把旧历史换成一段摘要。上限是多少？取决于模型的 **context window**（上下文窗口，即模型单次能处理的最大 token 数量）：

```rust
// codex-rs/model-provider/src/provider.rs:552 —— 一个模型的例子
"context_window": 272_000,
"max_context_window": 272_000,
```

> 不同模型的上下文窗口差异很大：这是 Codex 官方模型的一个例子（272K），而 DeepSeek V4 Flash 的上下文长达 **约 1M token**，95% 余量对应的窗口硬上限约 950K（注意：这只是防止超限的兜底上限，日常压缩的触发点是独立的 `auto_compact_token_limit` 预算，通常更小）。顺带一提，这个 272K 与第 4 节的 272K 计费阈值仅是数值巧合——前者是 context window 配置、后者是计费跳档规则，二者无关。

不过要先分清：**常规压缩的触发点并不是"95% 的上下文窗口"，而是一个独立的 token 预算 `auto_compact_token_limit`**——可来自配置 `model_auto_compact_token_limit` 或模型元数据（[`codex-rs/models-manager/src/model_info.rs:35`](https://github.com/openai/codex/blob/57f42a8113/codex-rs/models-manager/src/model_info.rs#L35)），它通常远小于上下文窗口（若未配置该预算，则回退到窗口硬限作为唯一触发条件），且会叠加一段回退缓冲（fallback buffer）。同时 Codex 不会用到 100% 的窗口，而是留出余量（默认 `effective_context_window_percent = 95`，见 [`codex-rs/models-manager/src/model_info.rs:172`](https://github.com/openai/codex/blob/57f42a8113/codex-rs/models-manager/src/model_info.rs#L172)；该值可被配置覆盖）——**95% 的窗口只是硬兜底上限，用于防止请求超限报错，不是日常压缩的触发点**。实际有效上限由 `model_context_window()` 计算（[`codex-rs/core/src/session/turn_context.rs:238`](https://github.com/openai/codex/blob/57f42a8113/codex-rs/core/src/session/turn_context.rs#L238)）：对 272K 窗口 + 默认 95%，即 272_000 × 95 / 100 ≈ **258K tokens**。

压缩的判定是"auto-compact 预算超了 **或** 窗口硬限到了"二选一（[`codex-rs/core/src/session/context_window.rs:76`](https://github.com/openai/codex/blob/57f42a8113/codex-rs/core/src/session/context_window.rs#L76)）：

```rust
let full_context_window_limit_reached =
    full_context_window_limit.is_some_and(|limit| active_context_tokens >= limit);
let token_limit_reached = buffered_auto_compact_limit
    .is_some_and(|limit| auto_compact_scope_tokens >= limit)
    || full_context_window_limit_reached;
```

**触发时机不止"token 用满"一种**：请求发出前的预采样、回合中 token 超限、以及模型切换（比如换到上下文窗口更小的模型）时，Codex 都会先压缩旧历史再继续。

**但压缩本身也是一次完整的模型请求，代价一点不低**：客户端要把**全量历史**（连同摘要指令）再发给模型一次，让它把旧历史总结成交接摘要，再用「保留的旧历史 + 摘要」重建一个短历史替换原历史。压缩可以由服务端或客户端执行，但**无论哪种方式，都需要把全量历史发送给模型处理一次**。其他 Agent 可能采用裁剪、检索、增量摘要等不同策略。

在窗口硬限触发的极端情况下，这次请求的输入可达**约 258K token**（若由 `auto_compact_token_limit` 触发，则输入量取决于该预算的配置值，通常更小）。如果最初对话只有 1000 token，那么压缩这一次的代价就可能是原始对话的**数百倍**，而且这还只是"为保住上下文而交的一次性整理费"。

另一个佐证压缩确实是"全量发送"的细节：本地压缩路径下，如果历史长到连压缩请求本身都超限，Codex 会**从历史最前面删掉一条再重试**（[`codex-rs/core/src/compact.rs:304`](https://github.com/openai/codex/blob/57f42a8113/codex-rs/core/src/compact.rs#L304)），源码注释点明"从头删"是为了保住前缀缓存——可见它是真的在整段发送、直到塞不下为止。

最后把计费和压缩两个机制拼起来看，会得到一个反直觉的结论。以 GPT-5.6 Sol 为例：它的上下文窗口高达 **1.05M**，即便按默认 95% 的窗口硬上限算，压缩最迟要到**约 997K** 才发生；但计费在 **272K** 就已经整段翻倍。也就是说，**对 GPT-5.6 Sol 这类有阶梯计费的模型，价格悬崖远早于压缩触发点**——要不要早点压缩、早点开新对话，主要由计费阈值决定，而不是上下文容量（纯线性计费的模型如 DeepSeek 没有"悬崖"，此结论不适用）。上下文还没满，钱包先满了。

## 6. 一个惯性思维的澄清：续旧对话真的比开新对话便宜吗？

有些人觉得"续旧对话有前缀缓存命中，肯定比开新对话便宜"。我们算一笔账。

假设旧对话有 10000 token、本次新增 100 token 的新指令，你选择把旧历史总结成 200 token 的摘要开新对话（但本次新增的 100 token 新指令，无论续旧还是开新都得发）。全部按 DeepSeek V4 Flash 价格（2026-08-07，平峰示例价）算：

- **续旧对话**：假设旧历史前缀全部命中缓存，旧历史 10000 × 0.02 元/百万 = **0.0002 元**，新增 100 × 1 元/百万 = **0.0001 元**，合计 **0.0003 元**；
- **若缓存失效**：旧历史按未命中价 10000 × 1 元/百万 = **0.01 元**，合计 **0.0101 元**；
- **开新对话**：摘要 200 + 新指令 100 = **300 token**，按未命中价 300 × 1 元/百万 = **0.0003 元**。

对比很有意思：

- **缓存命中时**：续旧 0.0003 元 = 开新 0.0003 元，**几乎打平**——50 倍折扣把重发历史的成本全抵掉了；
- **缓存失效时**：续旧 0.0101 元是开新 0.0003 元的 **约 34 倍**；
- 再看账单结构——即使缓存命中打了 50 折，**前面的旧历史（0.0002 元）仍是新增内容（0.0001 元）的 2 倍，占账单 67%**。折扣只会让"旧历史"变便宜，但当历史量足够大时，它依然是账单大头。

换成 **GPT-5.6 Sol**（缓存折扣只有 10 倍，美元计价），同样的账更刺眼：
- **续旧（缓存命中）**：10000 × 0.50 美元/百万 + 100 × 5.00 美元/百万 = **0.0055 美元**；
- **续旧（缓存失效）**：10000 × 5.00 美元/百万 + 100 × 5.00 美元/百万 = **0.0505 美元**；
- **开新对话**：(200 + 100) × 5.00 美元/百万 = **0.0015 美元**。

缓存命中时，续旧（0.0055 美元）仍是开新（0.0015 美元）的 **3.7 倍**——10 倍折扣补不回重发历史的开销；缓存失效时同样约 **34 倍**。对比一下：**同是缓存命中，DeepSeek 的 50 倍折扣让续旧≈开新，GPT-5.6 Sol 的 10 倍折扣则让续旧贵出 3.7 倍——折扣越小，续旧越贵。**

> 需要说明：以上只看**单次请求的 token 费用**。开新对话省的是"重发历史"的钱，但你自己总结成 200 token 摘要是有成本的（时间，或让模型总结的费用），而且摘要质量下降可能让模型在后续多轮中犯错、多花更多轮的 token——真实成本未必更低。另外以上均为**平峰时段**价格；若所在时段单价上浮（如 DeepSeek 高峰时段翻倍），绝对费用整体抬升，但续旧/开新的**比值不变**，本节结论不依赖平峰/高峰。

关键变量是**缓存是否命中、折扣有多大**：折扣越大（如 DeepSeek 的 50 倍），续旧对话越接近"近乎免费"，开新对话的省钱优势被抵消，但代价是丢上下文；而如果服务商**没有实现前缀缓存**（比如某些中转站），旧历史直接按未命中全价算——历史越长越亏，此时"自己总结摘要、开新对话"就是非常明智的选择。更进一步，像 GPT-5.6 Sol 这类超过 272K 输入就整段翻倍计费的模型，历史一旦跨过阈值，续旧对话的单价还会整体跳档。attention 计算量也是同理：续旧的增量计算（≈2×10000 = 20000 格）已经约等于新对话的全量计算（100×100 = 10000 格）的两倍。

那为什么我们还会去续旧对话？因为**新对话没有上下文**——模型不记得之前的决策、约束和进度。所以这是一个定价上的两难：

> **要上下文，就要为越来越长的历史持续付费；要便宜，就丢掉上下文从零开始。**

<a id="conclusion"></a>

## 7. 结论

把全文串起来，核心事实只有一条：**从 API 使用者的视角看，大模型通常是无状态的——每发起一次新的推理请求，客户端都要重新提供当前上下文。**

- Agent 怎么理解模型输出？—— 靠**类型化的结构化事件流**，不是靠扫描字符串。
- 模型的"记忆"哪来的？—— 靠**每次全量重发历史**，不是靠 KV cache。
- 代价如何增长？—— 见第 4 节的三层账本：token 数**线性**涨、单价**会波动**、self-attention 部分**二次方**涨，前缀缓存只缓解不消除。
- 超限了怎么办？—— **压缩**，但压缩本身就是一次全量重发的请求，代价高昂。
- 新对话 vs 续旧对话？—— 新对话便宜但没上下文，续旧对话贵但记得事。

理解这一点，你就理解了为什么长会话那么烧钱、为什么 Agent 需要压缩、为什么"缓存"和"记忆"是两个完全不同的概念。**上下文不是模型的属性，而是你花 token 买来的。**
